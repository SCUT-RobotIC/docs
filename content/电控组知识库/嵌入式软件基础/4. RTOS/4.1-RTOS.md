随着学习的深入，你也会重新产生新的疑问。比如：如果只是为了保持实时性，使用一个抢占一切任务的RTOS任务和一个优先级很高的中断又有什么区别呢？这主要是在于，任务在运行过程中和间隙可能会等待信号量，可能会等待外设，RTOS可以允许在这些时间中主动让出CPU让优先级更低的任务进来，尤其是，你在中断中原则上就不应该让任务等待。这就给程序设计和运行带来了更多灵活性。又比如说，你可能觉得1000Hz的sysTick导致高于1000Hz的任务不能在RTOS中运行，但实际上完全可以用硬件定时器驱动一个事件，在有抢占式调度的情况下用它触发任务的运行，这仍比纯定时器调度带来更大的灵活性和稳定性。这里可能涉及了一些你目前还不了解的概念，但是当你真正学到这些概念的时候，可能你会想起这些。

	我们在开发环境接触到的RTOS功能函数都由兼容层CMSIS_RTOS定义（一般以os开头），而其底层功能由FreeRTOS实现（一般以x/v/pv/...开头，用以标注返回值类型）。这样的好处是代码的可移植性强，更换系统内核可以不改动应用层代码。

	在CUBE移植的版本中，默认包含heap_4实现，不同的数字表示了不同的内存管理策略。heap_4的策略大致是块链表+首次适配+碎片合并，具有比较均衡的内存开销、实时性和碎片化控制表现。

### 一、任务管理
#### 1. 任务的创建
**你可以直接使用CubeMX创建任务**，然后重新生成代码即可。参数设置参考下文。

![Pasted image 20260407201526.png](<assets/Pasted image 20260407201526.png>)

使用CubeMX创建的任务（在CMSIS_OS中，统称为thread。在一些复杂操作系统中会区分process和thread的概念，此处按下不表）会在`MX_FREERTOS_Init()`中被集中创建，它位于调度器启动之前（`osKernelStart()`。当然，这不代表内核启动后不能新建任务）。使用函数`osThreadNew()`创建任务（对应FreeRTOS中的`xTaskCreate`）。

实际上这个功能调用的函数是`osThreadNew`。这个函数的函数原型是：
```C
osThreadId_t osThreadNew (osThreadFunc_t func, void *argument, const osThreadAttr_t *attr)
```

其中，func为运行任务的函数（对应cube中的enty function。这个名字可以任意，任务的标识符的名字在attr中定义）。`osThreadFunc_t`的类型定义是 `typedef void (*osThreadFunc_t) (void *argument);` ，这是一个函数指针，所以func是一个返回值为void的函数，并且接收参数`void *argument`。同时，任务函数应该永远不返回（没有return）。

argument为传入的参数列表，不过这个参数只能在任务启动时传入。`void*`是无类型指针，它的使用方法如：
```C
int a = 10;
void* p = &a;
int* int_p = (int*)p;
```
在cubeMX配置中，这里对应Parameter输入框。
attr为描述任务属性的结构体，包括标识符（对应task name，默认必须在16字节以内）、栈空间、任务优先级等。
**不能在中断服务程序（ISR）中创建任务。**
##### 栈空间
在attr中，内存以Byte为单位，但**在cube中，内存以word为单位**，在32位MCU中1word=32bit=4B，所以在CUBE中配完会帮你自动x4。栈空间决定了任务可以使用的用于存储局部变量、函数参数和调用栈、各类上下文的空间。除非任务被终止，否则这些分配的内存会被单一任务持续独占，所以应当设置合理的内存大小。一般来说，普通任务可以给128Words（512B）空间。当然，我们有办法实时监控任务占用的空间。作为参考，STM32H723ZGT6具有564KB的SRAM，CUBE默认堆内存总量为15360B（15KB），所有任务栈、队列、信号量等动态对象都从该堆中分配，当然，除此以外的全局变量等不受堆内存的管理。
##### 属性位（attr_bits）
##### 内存分配方式
在CUBE可以设置任务栈是静态分配还是动态分配。使用动态分配时，不指定attr中的`stack_mem`，反之则手动指定。静态分配内存的任务无法释放内存。
##### 线程优先级
cmsis_os定义的优先级等级由低到高分为low, below normal，normal, above normal, high和realtime，每个等级内还有数字细分分级。
#### 2. 任务的状态
在CMSIS_OS中，任务有以下几种状态：
- Inactive（非活动）：常见于任务已创建但未加入调度，或已被删除，对应FreeRTOS中的挂起态(eSuspended)，不能进入运行态
- Ready（就绪）：准备运行，等待CPU分配时间，可以进入运行态
- Running（运行）：正在占用CPU运行
- Blocked（阻塞）：任务正在等待，依赖未满足，不能进入运行态。一般来说和挂起的区别是阻塞有超时时间，可以自行恢复
	常见的情况一般有：处于delay中（这个delay必须使用os_delay），等待消息队列、信号量、互斥锁等等
- Terminated（终止）：任务不再运行
- Error（错误）

#### 3. 任务的调度
内核启动之后，任务开始由调度器执行。调度器会按照优先级的高低顺序逐个运行就绪任务，如果没有任何要运行的任务，则进入空闲任务。

应该说，任务调度是引入RTOS的最重要目的，也正是为了这个目标，我们花费大量额外内存资源来保存各个任务的状态（上下文）。它允许调度器保存任务当前状态，并随时切换到其它任务，这使得复杂的任务调度系统成为现实。
##### 时间片流转
在RTOS中，同优先级任务之间可以通过时间片流转进行调度。
时间片流转实际上就类似于我们通过TIM定时器实现的多任务系统（假设中断优先级都一样），但区别是所有任务都只能最多运行一个时间片的长度，如果程序运行超出时限并且没有主动让出CPU（比如进入阻塞或挂起），那么调度器会保存程序的当前状态，然后强制切换到下一个任务。

也就是说，调度器会在以下情况下切换任务：
- 当前任务主动阻塞（调用 `delay`、等待信号量等）
- 当前任务主动让出 CPU（调用 `taskYIELD()`）
- 更高优先级的任务变为就绪
##### 抢占式调度
为了保证高优先级任务的实时性，高优先级任务可以直接打断低优先级任务的运行，而低优先级任务只能等待。**时间片流转只能被用于同优先级任务的调度**，如果一个任务的优先级高于系统中所有其他就绪任务，时间片流转就对他无效，甚至把低优先级任务“饿死“。所以，这种高优先级任务时往往被设计成**事件驱动**且**单次处理时间极短**的任务。

> [!Note] 优先级反转和继承
> 如果一个高优先级任务需要依赖一个低优先级任务的消息，那么这个高优先级任务反而会受到低优先级任务的制约，甚至被低优先级任务阻塞，这就是优先级反转现象。如果想要解决它，可以使用的方法是优先级继承，将高优先级所依赖的低优先级任务临时继承高优先级任务的优先级，以便尽快完成，避免阻塞高优先级任务。

#### 4. 任务的同步
任务之间可能需要一些状态量或者参数的传递来进行同步，没有使用FreeRTOS之前，我们往往使用的方法是使用公共全局变量。但是，这么做是有风险的。首先需要知道，如果共享资源比较复杂（比如它是一个结构体，或者涉及浮点数运算等等），那么读取和修改这个状态的操作有可能是非原子性的（也即，CPU在运行这个任务的时候需要运行多条指令，这意味着这些指令中间可能被插入其它指令）。
- 如果有多个任务同时修改一个数据，那么这个公共资源的值不可预测。这被称为**数据竞争**（数据竞争是竟态条件的一种体现）
- 多个线程/进程同时访问共享资源，且至少有一个操作是写入时，由于操作顺序不确定，最终结果可能因线程调度差异而不同（比如，如线程A检查资源可用后准备使用时，线程B已抢先修改状态，导致A的操作基于过期数据）。这被称为**竞态条件**（扩展阅读：[竞态条件（Race Condition）问题](https://www.cnblogs.com/irobotzz/p/18723638)）
- 公共资源有可能在其被某个任务函数读取的期间发生改变（要记得，修改可能是非原子操作），导致数据异常。这被称为**中间状态暴露**。
- 并且，这种组织方式会导致追踪是谁修改了公共变量变得困难，也不利于我们梳理消息的产生和消费。
所以，在FreeRTOS中，引入了一些更加高级的同步方式。

>[!Question] 听起来很吓人……
>但是好像之前写的那些裸机代码也没出过什么奇怪的问题，不是吗？
>这可能是因为：
>- 默认情况下，变量应该存储在它的**大小整数倍**的地址上。对于Cortex-M核心来说，对齐的8/16/32位**简单加载/存储**是原子的（这包括**单次**赋值或读取变量值，其它操作不能保证，并且long long和double不在其中），所以简单的数据读写可能不会引起竟态条件。（对了，默认的意思就是你可以手动不让他这么做。但是对于Cortex-M0核心，非对齐访问会引起hardfault，对于M3/M4，这种访问也是非原子的。详见有关内存部分文章）
>- 如果你不手写链表之类的复杂数据结构，修改共享资源的非原子操作实际上也只占用不太多的CPU周期，并且你会发现在裸机编程中唯一可能导致竟态的是各种中断，但是其触发周期（对于CPU来说）并不是很高，发生竟态的概率不大。
>- 你的代码对竟态不敏感，出了问题也没发现。
>
>其实，哪怕写裸机代码，照样有一些对于竟态非常敏感的任务需要额外的保护。这个时候往往使用的手段是临界区保护：
>```C
>void fun(){
>	__disable_irq();    //进入临界区，不允许新的中断触发
>	//关键操作
>	__enable_irq();     //离开临界区，重启中断
>}
>```
>在RTOS中，任务切换频率远高于中断（可能每毫秒一次），多个任务平等竞争，没有“主循环”的概念，临界区更长（任务代码比ISR长得多），资源竞争更激烈（更多任务访问同一资源），所以更应该注意这些问题。

C++加入了更多有关原子操作的原生支持，具体可查看C++相关文档。
##### 互斥锁（Mutex）
互斥锁的作用是独占共享资源，以便在我们在共享资源上锁期间可以安全地访问和修改这些资源，而不用担心它们会被其它进程调用。直到解锁，这些资源才可以重新被其它任务占有。

互斥锁的作用目标不是资源本身，而是**访问资源的行为**。需要使用同一个共用资源的所有行为必须使用同一个互斥锁，只有互斥锁被占有成功，才会真正进行数据的修改，而顾名思义，互斥锁只能被一个任务占用，所以一旦互斥锁占用失败，就说明别的任务正在使用资源，于是其它任务就不能对这个任务进行修改，从而达到锁定资源的效果。

互斥锁的一般使用形式是：
```C
osStatus_t status = osMutexAcquire(mutex, timeout);  //上锁
if (status == osOK) {
    // 上锁成功，操作共享资源
    // ...
    osMutexRelease(mutex);  //释放锁，以便其它任务使用
} else {
    // 上锁失败，执行错误处理
}
```

锁具有**粒度**的概念。指的是锁所保护的数据范围或代码范围的大小。可以想到，锁的粒度不是由锁本身决定的，而是取决于**在上锁期间做了什么**。上锁期间调用的共享资源越多，这个锁的粒度就越粗。

可以想见，为了保证程序的运行效率，应该尽量使用细粒度的锁，而锁的粒度粗细则完全取决于代码的设计。一般来说，**在锁内只做应当原子性完成的任务。**

>[!Note] 死锁
>死锁是指互斥锁所因为依赖关系而永远无法解锁的情况。比如，如果任务A先获取了mux1，同时B获取了mux2，这时候如果A想要再获取mux2，而B想再获取mux1，两边就会同时等待对方释放互斥锁，并且一直等下去。这告诉我们要谨慎对待锁套锁的情况，如果我们一定要写锁套锁的结构，就必须保证在所有任务中两个锁的获取顺序是一致的。
##### 信号量（Semaphore）
信号量用于任务同步（二值信号量）或管理资源池（计数信号量）。CMSIS 统一使用 `osSemaphore`管理，通过初始值区分用途。
信号量可以用CubeMX管理。
![Pasted image 20260407225504.png](<assets/Pasted image 20260407225504.png>)
使用方法如下：
初始化：
```C
osSemaphoreId_t bin_sem;  // 二值信号量（同步）
osSemaphoreId_t count_sem; // 计数信号量（资源池）

void init(void) {
    // 二值信号量：初始值 0，最大值 1（用于任务同步）
    bin_sem = osSemaphoreNew(1, 0, NULL);
    // 计数信号量：初始值 5，最大值 5（表示有5个可用资源）
    count_sem = osSemaphoreNew(5, 5, NULL);
}
```
获取信号量（返回osOK，说明信号量为ok或值被+1。每获取）：
```C
osStatus_t osSemaphoreAcquire(
    osSemaphoreId_t semaphore_id,  // 信号量句柄
    uint32_t timeout               // 超时时间（单位：时钟节拍）
);
```
释放信号量（将信号量的计数值+1，或发送ok ）：
```C
osStatus_t osSemaphoreRelease(osSemaphoreId_t semaphore_id);
```
获取计数信号量的计数值：
```C
uint32_t osSemaphoreGetCount(osSemaphoreId_t semaphore_id);
```
删除信号量（**一般不需要**）
```C
void osSemaphoreDelete(osSemaphoreId_t semaphore_id);
```
所以，二值信号量看起来像是一个开关，用于让一个任务控制另一个任务是否运行（当然，这种任务最好是循环step的任务），而计数信号则是在维护一个有限的资源水池，可以通过release加水，也可以通过acquire放水。

信号量可以干什么呢？它可以是两个串行功能之间的通信，一个工序干完，该下一个干。还可以用来设计调度器-功能函数结构，一个调度器管理多个并行的功能函数，通过计数信号量对并行的任务数量进行管理，再用一个消息队列给他们所有函数传参。
##### 消息队列
顾名思义，消息队列是一种用于传输消息的队列（queue）。它的好处是可以给消息产生和消费提供缓冲，并且天然支持引入多个消息产生者。
可以使用CubeMX管理消息队列（但是我觉得有点笨重）。
![Pasted image 20260407225311.png](<assets/Pasted image 20260407225311.png>)

在代码中，使用`osMessageQueueId_t osMessageQueueNew (uint32_t msg_count, uint32_t msg_size, const osMessageQueueAttr_t *attr)`创建队列。消息队列不关心所传递内容的类型，但是单个消息所占的内存大小是非常关键的，其内部使用memcpy来直接复制这个内存段，一般使用sizeof设定即可（类型本身也是可以使用sizeof的）。

使用`osStatus_t osMessageQueuePut (osMessageQueueId_t mq_id, const void *msg_ptr, uint8_t msg_prio, uint32_t timeout)`给消息队列插入消息。msg_ptr的对象比较自由，可以是结构体等；优先级是一个非负整数，0为最高优先级。

>[!Note] 中断安全性
>FreeRTOS的很多功能函数具有中断非中断的区分，用于中断的函数往往以fromISR（ISR即终端服务函数）作为结尾，这样做的主要原因是在中断中运行的程序往往需要更快，而且最好不要引入新的中断避免卡死。更多信息可以参考[这篇文章](https://zhuanlan.zhihu.com/p/439113270)
>
>不过好在，CMSIS兼容层会自动判断系统是不是处于中断中，从而决定是否使用带fromISR的函数，所以os函数不存在中断和非中断之别，可以直接使用。
>（如果你好奇这是怎么做到的，CortexM处理器中具有IPSR寄存器，用于指示系统是否处于ISR中）

>[!Attention]
>创建消息队列和往消息队列添加消息这个过程不需要有调度器参与，所以可以安全地在调度器启动前运行（这个情况可能会出现在你在硬件中断中添加消息的时候）。但是，在这个时候不能使用任何任务调度和软件中断相关的API，这要求我们必须设置0等待时间
##### 事件标志组（Evnet Flags）
事件标志，即FreeRTOS中的事件组（Event Group）。由于FreeRTOS中事件组的理念和CMSIS的要求不太相同，所以在CMSIS中只有创建、删除事件的实现，剩下的只能采取FreeRTOS的原生实现。

FreeRTOS事件组是FreeRTOS提供的一种轻量级同步机制，用于任务间的事件通知和同步。它通过一个32位的位掩码（EventBits_t）来管理多个事件标志，每个位代表一个独立的事件。

CMSIS中对事件标志的概念定义详见[CMSIS-RTOS2: Event Flags](https://arm-software.github.io/CMSIS_6/latest/RTOS2/group__CMSIS__RTOS__EventFlags.html)
##### 任务通知（Task Notification）
任务通知是FreeRTOS特有的特性，需要手动调用FreeRTOS的实现函数。
### 二、中断 
#### 1. ISR的纪律
在《程序设计的思维》中我们说过"ISR越短越好"，在RTOS中这条纪律有了更具体的约束：

- ISR里原则上只做三件事：**清标志、搬数据、发通知**。解析、计算、控制之类的重活不要在ISR里做
- 等待类操作一律禁止（osDelay、带超时的等待等），CMSIS API的timeout参数只能填0。原因很朴素：ISR打断的是当前任务，它等待的资源往往需要其它任务来生产，而其它任务此刻正被你压着——这在逻辑上就是死锁
- 不能在ISR中创建任务（见任务创建小节）

#### 2. 延迟中断处理
把"事件响应"和"事件处理"分开：ISR只负责喊一嗓子，重活交给专门的任务。这就是延迟中断处理（Deferred Interrupt Processing）模式：

```C
/* 中断回调：只报告事件，不干活 */
void KeyIRQ_Callback(void)
{
    osSemaphoreRelease(key_sem);       // 一句话：出事了
}

/* 专职任务：等通知，干重活 */
void KeyTask(void *argument)
{
    for (;;) {
        osSemaphoreAcquire(key_sem, osWaitForever);
        // 消抖、长短按判断、界面刷新……全在这里做
    }
}
```

这个结构的响应速度并不慢：ISR释放信号量的瞬间，等待它的最高优先级任务立刻抢占运行——实时性由优先级保证。而重活全部发生在任务上下文里，可以用全部API、可以阻塞、被打断也无妨。

#### 3. 中断优先级与调度器的边界
部署章说过：启用FreeRTOS后，所有会调用RTOS API的中断，NVIC优先级数值必须处于5-15。现在可以说清楚这条规矩的来历。

FreeRTOS内核也有"临界区"：修改调度链表、队列等内核数据时，必须保证没有任务切换插进来。它的做法是短暂屏蔽数值5-15这一段中断（通过BASEPRI寄存器实现），而**绝不屏蔽数值0-4**——最高紧急度的硬件需求（比如电机刹车保护）任何时候都不该被软件挡住。

代价随之而来：**数值0-4的中断里绝对不能调用任何RTOS API**。因为内核屏蔽中断做关键操作的那一刻，这些API依赖的内核数据可能正改到一半，此时调用它们轻则静默失败、重则HardFault，而且几乎不可复现。

>[!Warning]
>新增中断时养成习惯：要么把它的优先级数值调到≥5，要么保证ISR里完全不碰RTOS API。二选一，没有折中。

### 三、内存管理
#### 1. FreeRTOS的五种堆策略
FreeRTOS内核本身不依赖标准库的malloc/free（为了可移植性和确定性），而是提供了五种可选实现（部署章提到的Cube默认heap_4）：

- **heap_1**：只分配、不释放。最简单也最安全，适合任务只创建不删除的程序
- **heap_2**：支持释放，但空闲块不合并，长期运行会碎片化
- **heap_3**：直接包装标准库malloc/free并加锁，堆大小由链接脚本决定
- **heap_4**：首次适配+相邻空闲块合并，开销、实时性和碎片化控制最均衡（**Cube默认**）
- **heap_5**：heap_4的多内存区域版本，可以把不连续的RAM拼成一个堆（比如H7的多块SRAM）

除heap_3外，它们管理的内存都来自`configTOTAL_HEAP_SIZE`定义的一块静态数组，所有任务栈、TCB、队列、信号量等动态对象都从这里分配（部署章说的15KB默认堆就是它）。

#### 2. 动态分配与静态分配
osThreadNew默认从堆中动态分配任务栈；它的对立面是在任务属性attr中手动指定`stack_mem`的静态分配（见任务创建小节）。

动态分配的风险是"运行期失败"：堆碎片化或耗尽时，创建任务返回NULL。**必须检查osThreadNew的返回值**。栈溢出好歹有症状，创建失败却什么都没有，这是新手任务"莫名不运行"的头号原因。

静态分配把风险提前到编译期：内存常驻、大小写死、不会悄悄失败，代价是不管任务是否运行都占着内存。对任务数量固定、长期运行的机器人代码，静态更稳；开发调试期用动态+检查返回值足够。

#### 3. 堆与栈的监控
堆剩余量：`xPortGetFreeHeapSize()`查当前；更有价值的是`xPortGetMinimumEverFreeHeapSize()`——历史最低水位，反映峰值用水，离0太近就该扩`configTOTAL_HEAP_SIZE`了。

任务栈监控：任务创建小节留下的"我们可以实时监控任务占用的空间"，指的就是水位线函数：

```C
UBaseType_t free = uxTaskGetStackHighWaterMark(handle);   // 单位：word
```

它返回该任务**历史上用过的最小剩余栈**。返回值越小越危险，经验上低于20 word（80B）就该加大栈。printf、浮点运算和局部大数组是吃栈大户，含它们的任务要重点盯防。

### 四、疑难解答
按症状快速定位，再跳转到对应章节：
- **任务完全不运行**：忘了`osKernelStart()`；任务函数写了return（任务应永不返回）；`osThreadNew`返回NULL没检查（堆不够/栈太大）——见任务创建、内存管理
- **HAL_Delay一用就卡死**：在任务中调用了HAL_Delay，它忙等不让出CPU，低优先级任务全部饿死，开了看门狗还会复位——见常用小函数
- **系统偶发死机且不可复现**：优先级数值<5的中断里调用了RTOS API——见中断章
- **偶发数据错乱**：共享资源没加保护，竞态条件——见任务同步
- **偶发HardFault**：十有八九是任务栈溢出——见下节

#### 与RTOS有关的hardfault问题
修25R2的时候就有一个这样的问题。
[【RTOS】FreeRTOS中的任务堆栈溢出检测机制 - 李柱明 - 博客园](https://www.cnblogs.com/lizhuming/p/15487221.html)

任务栈溢出的机理：任务栈向下增长，写穿栈底后踩到的是**相邻内存**——可能是别的任务的栈，也可能是内核链表。踩到谁，症状就是谁：数据悄悄错乱、链表损坏、或者直接HardFault。所以它的表现极其漂移、几乎不可复现，是疑难解答里最阴险的一类。

排查三板斧：
1. **打开溢出检测**：`configCHECK_FOR_STACK_OVERFLOW`设为2（CubeMX的FreeRTOS配置页可勾选）。调度器每次任务切换时检查栈尾"水印"和栈指针位置，发现越界立刻调用`vApplicationStackOverflowHook`，钩子的`pcTaskName`参数直接告诉你**是谁**溢出。注意它只在切换时检查，溢出瞬间到下次切换之间的破坏抓不住，所以=2也不是百分之百
2. **水位线巡检**：用`uxTaskGetStackHighWaterMark`逐个检查任务（见内存管理章），找出水位线最低的那个
3. **修复**：加大该任务的栈。含printf的任务尤其注意——printf家族轻松吃掉几百字节栈；反复溢出的任务可以改静态分配，把隐患暴露到编译期
