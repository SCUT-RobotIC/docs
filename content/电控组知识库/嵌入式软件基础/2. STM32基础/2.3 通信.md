## 串口（UART）

### 帧结构
- **区分串行通信和并行通信，理解串行通信的优势**
- **理解什么是同步和异步、单工和全双工和半双工**
- **复习什么是LSB，什么是LSB first**
- **【扩展】了解什么是CRC校验**

UART（Universal Asynchronous Receiver/Transmitter，通用异步收发器）是最基本的串行通信方式，俗称串口通信。它是一种**异步**串行通信协议，可被配置为全双工。没有时钟线，收发双方靠事先约定的波特率各自采样。

计算机一次通讯发出来的一个基本数据单元被称为一个数据帧。常见的串口数据帧包含：
```
空闲(高) 起始位(低) D0 D1 D2 D3 D4 D5 D6 D7 校验位 停止位(高)
```

- **起始位**：一个低电平。接收方检测到这个下降沿就开始按波特率采样。
- **数据位**：5~9 位，通常是 8 位（STM32只支持8位和9位的情况），低位先发（LSB first），这里面放置了我们要传达的信息
- **校验位**：奇校验或偶校验，可选。不过实际上由于校验位的能力有限，实际项目里基本依靠上层代码在软件中实现，这一位基本不使用。
- **停止位**：1 位、1.5 位或 2 位的高电平，给接收方一个表示帧结束的缓冲。

8位数据、无校验位、1位停止位是常见的串口配置，可以被简写为**8N1**。显然，8N1的一个数据帧可以正好传输1Byte的数据。

### 波特率
- **理解什么是波特率**
- **在串口通信的场景下，波特率和比特率有区别吗？**

讨论波特率的时候我们讨论的是物理层信号调制的速率，因此不扣除开始位、停止位等控制符号。
常用的的波特率挡位有9600，115200，460800，921600等。

>[!Tip] 为什么波特率不是整数？
>你会发现，他们都是300的倍数。这主要是由早期的电话网络而来的习惯。1962年的Bell 103调制解调器传输速率为300bps，这在后来成为了电话网络的事实标准。在那之后，所有常见的串行数据传输速率都是这一速率的整数倍。
>
>当然，STM32的分频器可以做到以1/16为步进进行任意分数分频，所以现在使用波特率并没有太大限制，主要是习惯沿用。
>

### 连接
UART一般没有固定的接口形状，可能使用杜邦线，自行约定线序的排线，DB9/DB25，或者type-C接口等等。不过归根结底，一次UART通信至少需要三根线：
- TX（Transmit，发送）：本端发送，对端接收。
- RX（Receive，接收）：本端接收，对端发送。

>[!Note] 地线不是可有可无的
>多数通信协议要求两个设备之间必须共地（差分信号除外）。这是因为单线信号上的高/低电平是**相对于地**定义的，两台设备各自供电时地电位不同，这个比较就失去了共同基准。因此在通信时，第三根GND一定要接。
### STM32的UART外设
HAL 为每个通信外设都提供三套接口：轮询（阻塞），中断和DMA，串口也一样。
在这个过程中，CPU要做的是以字节为单位把数据塞进寄存器里面，剩下的具体协议保持和数据发送则是由UART外设自己完成的，这一点在代码中也能感受到。
#### 三种收发方式
##### 阻塞收发
- 阻塞发送：CPU自行把字节一个一个写进串口的数据寄存器（data register, DR），然后原地等待硬件发完，再写下一个；
- 串口接收：CPU在原地轮询等待RXNE标志位（Read data register not empty，表示数据已就绪）置位，此时触发中断服务函数。从DR读出字节存进缓冲区，循环Size次才返回。

>[!Tip] 标志位和寄存器
>标志位和数据寄存器实际上没有本质区别，他们都是寄存器，只不过标志位往往指的是那些只有一位、表示状态的寄存器，而数据寄存器可能就是很多位了，它用来存储收发的数据。
##### 中断收发
- **中断发送**：调用函数只把缓冲区指针和长度传递给句柄，使能TXE（Transmit data register empty，发送数据寄存器空）中断就立刻返回。之后硬件每把一个字节移位发完，TXE就置让CPU把缓冲区下一个字节写进DR，指针前移、计数减一；计数减到零关掉TXE中断，等DR里最后一个字节也发完，调用`HAL_UART_TxCpltCallback()`。
- **中断接收**：调用`HAL_UART_Receive_IT()`同样记下缓冲区地址和长度后返回，等RXNE置位。对端每发来一个字节，RXNE发起中断，**由CPU从DR读出字节**放进缓冲区、计数减一；攒满Size个字节关则调用`HAL_UART_RxCpltCallback()`。

好吧，CPU 还是要搬数据，不过这次至少不用一直等着了。

>[!Tip] 有关DR寄存器
>你有没有想过如果发送和接收都用数据寄存器DR，那么UART是怎么实现全双工的？
>实际上，DR其实不是指一个寄存器，而是两个物理独立的寄存器共用同一个地址。
##### DMA收发
那CPU可以不自己搬运数据吗？方法前面提过，那就是使用DMA。

调用传输函数时候，CPU配置源地址（串口 DR）、目的地址（缓冲区）、长度、方向和递增模式，然后使能、立刻返回。之后这 Size 个字节就与 CPU 无关了：
- 串口硬件每就绪一个字节（RXNE/TXE），就向 DMA 发一次**请求**，**DMA 控制器自己**把字节在 DR 和缓冲区之间搬过去、地址加一、计数减一——整个过程不执行任何 CPU 指令，也不进任何中断
- 直到计数减到零，DMA 才发**一次**中断叫CPU收尾，走同样的 `TxCpltCallback` / `RxCpltCallback`。

对比一下中断方式，收 1000 个字节要进 1000 次中断（每次都有压栈恢复现场的开销），而DMA只需要进1次。一般来说，波特率如果比高于115200，或者同时需要管理多个串口时，建议考虑DMA。

> [!Note] 缓冲区与数据竞争
> 一串数据不是立刻被串口收发的，所以需要暂存在一个地方，这就是缓冲区。第一级缓冲区在我们设置收发函数时就会传入，直接由CPU或DMA读写，占用的大小等同于收发的数据本身的大小。但是，这也意味着字节一到就会写进去，如果主循环此时还在解析上一帧，下一帧已经开始覆盖同一个数组，读到的就是半新半旧的混合体，这就产生了数据竞争。
>
> 问题的本质是**生产者（串口硬件/DMA）和消费者（主循环解析）的节奏和速度有可能对不上**。可能最省事的做法是收到数据当场在回调里解析、执行，但这和我们对中断代码的要求不太符合。这样做的结果是中断变长，解析期间低优先级中断和主循环全被挂起，串口设备太多或者高波特率时，CPU可能来不及从DR中读取数据，下一帧就已经来了，从而产生溢出错误（特点是ORE标志位置位）。所以这种做法往往只适合简单协议的解析。
> 
> 所以，更好的办法是额外手写一块缓冲区做中转，把两边解耦。常见的写法是在接收完成回调里，只将DMA缓冲区里的数据拷贝到另一块"解析缓冲区"，而在主循环中处理后者。常见的这种手写缓冲区实现有两种：
> - **环形缓冲区（FIFO）**：中断写尾指针、主循环读头指针，两个指针在数组里循环追赶。
> - **双缓冲（乒乓）**：两块缓冲区交替，DMA填A时主循环解析B，靠半传输/完成中断交换角色。接收与处理完全重叠，常见于连续采样、音频这类流水线场景。
> 两种缓冲区的实现已有很多，大家可以自行了解。
> 
> 需要注意的是，缓冲区的作用是解决双方的**节奏不匹配**，容许生产者的突发传输或者消费者的突发忙。但如果平均下来消费速度永远低于生产速度，再大的缓冲区也一定会溢出。所以首先要保证的永远是两边平均速率的匹配，而缓冲区只用来吸收抖动。

#### 函数原型和基本实现

```c
/* 轮询 */
HAL_StatusTypeDef HAL_UART_Transmit(UART_HandleTypeDef *huart, uint8_t *pData, uint16_t Size, uint32_t Timeout);
HAL_StatusTypeDef HAL_UART_Receive (UART_HandleTypeDef *huart, uint8_t *pData, uint16_t Size, uint32_t Timeout);

/* 中断 */
HAL_StatusTypeDef HAL_UART_Transmit_IT(UART_HandleTypeDef *huart, uint8_t *pData, uint16_t Size);
HAL_StatusTypeDef HAL_UART_Receive_IT (UART_HandleTypeDef *huart, uint8_t *pData, uint16_t Size);

/* DMA */
HAL_StatusTypeDef HAL_UART_Transmit_DMA(UART_HandleTypeDef *huart, uint8_t *pData, uint16_t Size);
HAL_StatusTypeDef HAL_UART_Receive_DMA (UART_HandleTypeDef *huart, uint8_t *pData, uint16_t Size);
HAL_StatusTypeDef HAL_UARTEx_ReceiveToIdle_DMA(UART_HandleTypeDef *huart, uint8_t *pData, uint16_t Size);
```

- `huart`：串口句柄，指向 CubeMX 生成的 `huart1` 等结构体，正是第一章"通过句柄传递参数"的用法。
- `pData` / `Size`：数据数组的首地址（指针）和**字节数**。
- `Timeout`：只存在于轮询版本，单位毫秒——收不到就返回 `HAL_TIMEOUT`

看完前面的章节就可以知道，中断发送直接用一条指令就结束了，但是中断接收和DMA接收则必须需要在中断回调函数当中处理

回调函数：
- 中断接收：
```C
/* 启动第一次接收，一般在main函数最开头 */
HAL_UART_Receive_IT(&huart1, rcv_it_buf, 16);
/* USER CODE BEGIN 4 */
void HAL_UART_RxCpltCallback(UART_HandleTypeDef *huart){
    if (huart == &huart1) {
		//对rcv_it_buf进行一些处理
    }
    HAL_UART_Receive_IT(&huart1, rcv_it_buf, 16);  /* 启动下一次接收 */
}
/* USER CODE END 4 */
```

- DMA接收：
```C
/* 启动第一次接收 */
HAL_UART_Receive_DMA(&huart1, rcv_dma_buf, 64);
/* USER CODE BEGIN 4 */
void HAL_UART_RxCpltCallback(UART_HandleTypeDef *huart){
    if (huart == &huart1) {
        //对rcv_dma_buf进行一些处理，Size 个字节已经由 DMA 填好
    }
    HAL_UART_Receive_DMA(&huart1, rcv_dma_buf, 64);  /* 启动下一次接收 */
}
/* USER CODE END 4 */
```

- DMA+空闲中断：
```C
/* 启动接收：用 ReceiveToIdle 代替 Receive_DMA */
HAL_UARTEx_ReceiveToIdle_DMA(&huart1, rcv_buf, sizeof(rcv_buf));
__HAL_DMA_DISABLE_IT(&hdma_usart1_rx, DMA_IT_HT);    //关闭半满中断

/* USER CODE BEGIN 4 */
void HAL_UARTEx_RxEventCallback(UART_HandleTypeDef *huart, uint16_t Size){
    if (huart == &huart1) {
        //Size 就是本次实际收到的字节数，收满或总线空闲任一事件先到都会进这里
    }
    HAL_UARTEx_ReceiveToIdle_DMA(&huart1, rcv_buf, sizeof(rcv_buf));
    __HAL_DMA_DISABLE_IT(&hdma_usart1_rx, DMA_IT_HT);
}
/* USER CODE END 4 */
```

实际上HAL_UARTEx_RxEventCallback默认会在空闲中断、缓冲区半满和全满中断时触发。如果我们不使用pingpong缓冲区，可以选择关闭半满中断。

除此之外，为了保证串口不会因为不稳定的接收死掉，最好自己实现以下错误处理回调函数，一旦出错也重开一次接收：

```C
void HAL_UART_ErrorCallback(UART_HandleTypeDef *huart){
  if(huart->Instance == USART1){
     HAL_UARTEx_ReceiveToIdle_DMA(&huart1, buffer, sizeof(buffer));
     __HAL_DMA_DISABLE_IT(&hdma_usart1_rx, DMA_IT_HT);
  }
}
```

为了防止接收太快中断来不及处理，一般都是**一次接收完以后在中断中开启下一次接收**，而发送一般是固定频率放在主循环或者定时器中断中。

> [!Note] 【扩展】DMA的错误处理行为
> 在前人文档里反馈过这样一个坑：如果只在`HAL_UARTEx_RxEventCallback`里面重开DMA接收，如果输入的波特率波动或者错误（这不一定是主观的，实际上硬件的噪声、线缆松动、上电时序等等问题都有可能触发错误），那么串口就会直接死掉，不会响应后面的接收。解决方法是把重开的代码放在IRQHandler中。
> 
> 你可能现在已经知道，串口错误时程序会进入`HAL_UART_ErrorCallback`，所以实际上实现错误回调并重开和这种做法是等效的，你可以思考一下这是为什么（提示：在DMA+空闲中断时，什么情况会触发IRQHandler？）。
> 
> 但是这里面有一个更加耐人寻味的问题：你可以试试不实现错误回调，然后将串口设成115200，然后用电脑给他一个9600波特率的包（这回触发FE错误置位），你会发现这时候中断回调函数虽然接收的数据是错误的，但是不会自己死掉，但是DMA却会。为什么DMA对错误更敏感呢？这是因为HAL库把DMA下的所有错误都认为是阻塞的，一旦有错误发生，就会自动取消所有DMA传输，包括已经启用的空闲中断，这就导致后续的空闲中断永远不会触发。而中断接收则不会这样做，实际上在出现错误的时候，`HAL_UART_RxCpltCallback`依然会被触发。

| 回调函数                          | 触发条件（底层中断源）                                                     | 典型用途                               |
| ----------------------------- | --------------------------------------------------------------- | ---------------------------------- |
| `HAL_UART_TxCpltCallback`     | 【中断/DMA】发送完成。中断方式是 TC 置位，DMA 方式是 DMA 通道传输完成（TCIF）               | 发送下一包、释放/复用发送缓冲区，不太常用              |
| `HAL_UART_RxCpltCallback`     | 【中断/DMA】收攒满 Size 个字节。中断方式是 RXNE 中断攒满，DMA 方式是 DMA 计数减到零          | 整帧解析；**中断方式必须在这里重新开启接收**（见上例）      |
| `HAL_UART_TxHalfCpltCallback` | 【仅 DMA】发送进行到一半（DMA 半传输 HTIF）                                    | 发送了正好一半的数据，发送侧较少用                  |
| `HAL_UART_RxHalfCpltCallback` | 【仅 DMA】接收进行到一半（HTIF）                                            | 多用于乒乓缓冲：半满 处理前半块，全满处理后半块           |
| `HAL_UART_ErrorCallback`      | 【**所有情况**】溢出 ORE / 噪声 NE / 帧错误 FE / 校验 PE，DMA 模式下还包括 DMA 总线传输错误 | 统一的出错入口；                           |
| `HAL_UARTEx_RxEventCallback`  | 【仅DMA+空闲中断】串口空闲 IDLE 中断（总线空闲一个字节时间）配合 DMA/IT 使用                 | **不定长帧**最常用：参数 Size 直接告诉你这次收到了几个字节 |

>

>他们是在什么时候被触发的呢？以`HAL_UART_Receive_IT()`为例，它的主要功能是做一些初始化之后调用`UART_Start_Receive_IT(huart, pData, Size)`，而后者的实现是这样的：
>```C
>HAL_StatusTypeDef UART_Start_Receive_IT(UART_HandleTypeDef *huart,
> 	uint8_t *pData, uint16_t Size){
>	huart->pRxBuffPtr = pData;
>	huart->RxXferSize = Size;
>	huart->RxXferCount = Size;
>	huart->ErrorCode = HAL_UART_ERROR_NONE;
>	huart->RxState = HAL_UART_STATE_BUSY_RX;
>	if (huart->Init.Parity != UART_PARITY_NONE)
>	{
>		/* Enable the UART Parity Error Interrupt */
>		__HAL_UART_ENABLE_IT(huart, UART_IT_PE);
>	}
>	/* Enable the UART Error Interrupt: (Frame error, noise error, overrun error) */
>	__HAL_UART_ENABLE_IT(huart, UART_IT_ERR);
>	/* Enable the UART Data Register not empty Interrupt */
> 	__HAL_UART_ENABLE_IT(huart, UART_IT_RXNE);
>	return HAL_OK'
>}
>```
>所以你就可以知道，除了RXNE，ORE和ERR也是可以触发`UARTx_IRQHandler`的。之后服务函数会自己通过寄存器的置位情况
>
>然后我们就可以解释一个你可能没发现的问题：我们前面一直说RXNE是按字节触发的，那为什么我们使用DMA+半满中断的时候可以放心地直接在IRQHandler里面重启DMA接收呢？其实是因为在DMA接收的时候**RXNEIE事件根本就没有被启用**（这个时候RXNE被DMA直接消费了），只有IDLE和错误的时候，IRQ才会触发。这也就解释了为什么在错误回调函数里面重启实际上和在IRQHandler的用户代码段重启是等效的。

> [!Note] UARTEx 和"半满"中断的命名
> 你会发现半满中断的回调叫`HAL_UART_RxHalfCpltCallback`——明明只是"收到一半"，名字里却带着`Cplt`（Complete，完成），看起来和"完成"类回调（`RxCplt`）重名了。这不是笔误，把它断开读就通了：`Rx | Half | Cplt` = "**接收半程完成**"，`Cplt` 修饰的是"半程"而不是整个传输。这个名字继承自 DMA 层——DMA 的世界里只有两个进度事件：传输完成（TCIF → `XferCpltCallback`）和半传输（HTIF → `XferHalfCpltCallback`），串口层只是把这两个事件原样转发成自己的回调，所以保留了 `HalfCplt`（半程完成）的措辞。这也顺带解释了为什么半满回调【仅 DMA】存在：HTIF 是 **DMA 计数器减半时**硬件置位的标志，纯中断方式根本没有"计数"这个概念，自然就没有"一半"可说。
>
> 再看`HAL_UARTEx_ReceiveToIdle_DMA`里的`Ex`后缀。HAL 库按源码文件把 API 分成两层：`stm32f1xx_hal_uart.c`是**核心模块**，只放全家族通用、从初版就稳定存在的基础功能；`stm32f1xx_hal_uart_ex.c`是**扩展模块**（Ex = eXtended），存放两类东西：只有部分型号才有的特性（其他家族的 RS485 收发使能、Stop 模式唤醒、FIFO 等），以及**后来才补进来的新功能**。`ReceiveToIdle`整组 API 属于后者：不定长帧的"事件模式"（句柄里新增的`ReceptionType`/`RxEventType`字段 + 统一的`RxEventCallback`出口）是较新版本才加入 F1 HAL 的，为了不动老 API 的结构体布局、不破坏旧工程兼容性，ST 把这套新机制整个放进了 Ex 模块。同样的命名规律到处都是：`HAL_TIMEx`（互补输出等扩展通道）、`HAL_ADCEx`（注入通道）、`HAL_CANEx`（过滤器组）——凡带`_Ex`，读作"基础功能之外的那些事"。
>
> 顺带一提：UARTEx 不是什么新外设，它和 UART 是同一批寄存器（RM0008 里也只有一个 USART 章节），**Ex 只是 HAL 库的文件组织方式**。所以你会看到 CubeMX 生成的工程里 `usart.c` 同时调用 `HAL_UART_Init()`（核心）和 `HAL_UARTEx_ReceiveToIdle_DMA()`（扩展）——它们操作的是同一个 `huart1` 句柄。

### 【扩展】串口的电平标准
UART本身规定了一致的数据帧格式，但是电平标准、连接器协议等其实有很多种。

你可以用多种方式表达信号电平0和1，这就产生了不同的电平标准：

| 标准    | 电平           | 拓扑    | 距离       | 典型场景           |
| ----- | ------------ | ----- | -------- | -------------- |
| TTL   | 0/3.3V（或 5V） | 点对点   | 几厘米      | 芯片之间、接 USB 转串口 |
| RS232 | ±3~±15V，负逻辑  | 点对点   | 约 15m    | 老式电脑串口、工控设备    |
| RS485 | 差分，两根线       | 总线，多机 | 可达 1200m | 工业现场、长距离多节点    |
单片机直出的串口使用的是 TTL 电平，**不能直接将RS232等其它电平标准的串口连接到一起**，需要通过芯片来转换。

另外，RS232和RS485通常使用DB9/DB25接口：

这东西在老电脑上比较常用，也可能当作CAN，JTAG，MIDI等设备的物理接口。可能你会觉得很眼熟：VGA在接口上使用的DB15接口也是它的兄弟。

>[!Note] 【扩展】共模噪声和差分信号
>长导线就像天线，会感应周围的电磁干扰，两台设备之间的地电位差也会叠在信号上。这些干扰**会作用在传输线的每一根线上**，这种一起涨落的分量就叫共模分量。
>
>由于地线和信号线的路径阻抗不同，实际上共模噪声通过非理想的地线（阻抗、环路）转化成了不对称的差模干扰，同时地线既是参考基准，又是回流路径，因此地电位并不一定始终可靠。而普通单端信号用信号线对地电压来判断电平，这就可能产生信号错误。
>
>对此，RS232的对策是把信号幅度做到十几伏，这样几伏噪声就淹没不了它，但这样做的极限也只能使信号可靠传输十几米。
>而差分信号换了思路：用两根线 A、B，传的不是对地电压，而是两者的**压差** $V_A - V_B$。信号电流在一根线上正向流动，在另一根线上反向流动，它们受到的干扰高度一致，因此做差就可以滤除占大头的共模分量，得到比较稳定的信号来源。使用差分信号的RS485最远可以达到1200米的传输距离。
>
>不过，无论是几十伏的信号电压还是差分信号，都无法直接通过STM32发出，这就需要额外的转换芯片了。这一部分到CAN通讯的地方应该还会提及。

### 【扩展】串口的上层协议
你会发现串口标准只规定了最基本的比特率传输方式，但是对于上面的数据链路并没有标准的定义（这一点学完CAN，SPI等协议后你的感觉会更加明显）。实际上串口有不同的上层协议，比如Modbus，XMODEM等等。大家可以自行了解。

> [!Info] 
> STM32F103虽然有一路CAN，但是一般CAN总线使用差分信号，这就意味着必须使用收发芯片，而一般最小系统板不具有CAN收发器（这也是为什么画最小系统板的任务中有一个扩展部分就是画这个）。当然，我们这里有一些有CAN收发器和接口的H723ZGT6，如果你学完了这一部分，可以来找我们要板子和电机真的跑一个控制流程看看。

CAN是一种常用的总线通信协议，最早由博世开发，是国际上应用最广泛的现场总线之一。
CAN具有不同的协议版本：
- Low-Speed CAN：最大速率125 kbps，目前已弃用
- **High-Speed CAN：又称CAN 2.0，标准CAN，最大速率1Mbps。下文称其为标准CAN或CAN。**
- **FD CAN：5-8Mbps，使用扩展帧格式**
### 物理层
- **CAN 为什么用差分信号？

CAN总线（包括标准CAN和FD CAN）使用差分信号通信，具有两条信号线CAN H/L，在空闲状态，CAN H/L均为2.5V，这种状态被称为**隐性电平**，表示**逻辑1**。与此相对的状态是**显性电平**，这时候CAN H为3.5V，CAN L为1.5V，表示**逻辑0**。

![Pasted image 20261114014210.png](<assets/Pasted image 20261114014210.png>)

CAN总线上需要并联2个120欧电阻（一般实现方式是在单个收发设备H，L间串联电阻）， 所有收发器使用开漏输出，当电平为隐性的时候，所有收发器近似处于高阻态，提供一个2.5V的弱驱动。当电平为显性的时候，至少一个收发器驱动强电平至1.5/3.5V。所以在 CAN 总线的“线与”逻辑中，**显性电平（0）会覆盖隐性电平（1）**。只要总线上有一个节点发送显性位，整个总线就被拉成显性状态。这是CAN实现总线仲裁的关键物理基础。
### 数据帧

![Pasted image 20261114014323.png|700](<assets/Pasted image 20261114014323.png>)

总线空闲状态为1。标准CAN数据帧解释如下：
- SOF：起始符，1bit0
- 仲裁段
	- ID：标准ID11位。
	- RTR（Remote Transmission Request）：1bit，为0表示数据帧，为1表示远程帧，远程帧不携带数据。远程帧主要用于主动查询信息（和IIC的主机向从机查询类似）
- 控制端
	- IDE（Identifier Extension）：1bit标准帧为0，扩展帧为1（注意IDE**在标准帧中属于控制段，只用于表示控制段的开始，在FDCAN中属于仲裁段**）
	- r0：保留位
	- DLC（Data Length Code）：4bit，数据段字节数，一个CAN数据帧可以是0-8个字节。
- 数据段
	- Data Field：0-64bit，数据正文
- CRC段
	- CRC：15bit CRC校验值，由发送方计算，接收方重新计算并比对。若不一致，丢弃该帧并请求重发
	- DEL：1bit，CRC停止符
- ACK段
	- ACK：ACK slot。发送方发送隐性（1），接收方若正确接收，则发送显性（0）作为确认。一个正确发送的信息需要由至少一个设备响应
	- DEL：1bit，停止符
- EOF：7bit，end of file

FDCAN的区别主要是：
- **FDF 标志**：经典帧的保留位 r0 恒为显性 0，FD 帧把这一位发成隐性 1，改称 FDF（Flexible Data rate Format）——这是接收方区分两种帧的依据；
- **数据变长**：DLC 的 4 bit 编码扩展，9~15 不再对应 9~15 字节，而是 12/16/20/24/32/48/64 字节，单帧数据最多 64 B；
- **双速率**：FDF 后新增 BRS 位，为 1 时从数据段起切换到更快的"数据位速率"（仲裁段仍用原速率），其后的 ESI 位声明发送方是否处于被动错误状态；
- **CRC 加强**：CRC 从 15 bit 扩展到 17/21 bit（按数据长度选择），数据段与 CRC 段不再逐位填充，只在固定位置插入填充位。

### 总线设计
#### ID
CAN的总线是发送-消费模型，对于CAN协议本身来说，消息附带的ID被用于**分类消息本身，而不是像地址一样标记设备**。总线上的所有设备地位平等，通过过滤器收取特定ID的数据帧来获取想要的信息。这使得除了只关注单一ID数据帧的设备-消息ID绑定模式（这也是电机控制时最常见的一种情况），CAN总线天然支持一对多广播（只需要过滤器允许特定ID的消息经过）。

#### 同步
由于CAN属于异步通讯，没有时钟信号线，连接在同一个总线网络中的各个节点会像串口异步通讯那样，节点间使用约定好的波特率进行通讯。特别地，CAN还会使用“位同步”的方式来抗干扰、吸收误差，实现对总线电平信号进行正确的采样，确保通讯正常。

在实际的CAN传输中，任何1位CAN数据在总线上传输需要经过以下时间阶段：

![Pasted image 20261114014722.png](<assets/Pasted image 20261114014722.png>)

$t_{q}$ 是CAN通信中的最小时间间隔单位，由BRP（Baud Rate Prescaler，波特率预分频器）决定。四个时间段功能如下：
- Sync_Seg（同步段）：1tq，用于强制对齐。总线上的所有节点都必须在这个时刻采样信号。这是保证 CAN 总线多主通信能够同步的基础
- Prop_Seg（传播段）：补偿信号在物理总线上的传播延迟
- Phase_Seg1（相位缓冲段 1）：用于补偿节点间的时钟振荡器误差，位于定义的采样点之前
- Phase_Seg2（相位缓冲段 2）：同上，位于定义的采样点之后
两个相位缓冲为采样提供了一定的裕度，使得如果采样时间有一定偏差，也可以正确采样信号。

CAN设备在空闲后接收到第一个SOF位的时候，会归零自身计时器后按Bit Time定义开始计时和采样（**硬同步**）。CAN标准要求位翻转的边沿必须位于同步段内，如果发现后续位的变化边沿超出同步段，则会微调两个相位缓冲时间（最大调整幅度就是上面的SJW）进行**重同步**。
- 如果边沿**出现在同步段之后**，说明接收方时钟偏快，节点会**缩短**后续的 Phase_Seg2 长度（最多缩短 SJW 个 tq​），相当于让位时间稍微变短，把采样点往回挪一点；
- 如果边沿**出现在同步段之内**，说明接收方时钟偏慢，节点会**延长**后续的 Phase_Seg1 长度（最多延长 SJW 个 tq​），相当于让位时间稍微变长，把采样点往前挪一点

可以发现，同步段的长度实际上会影响CAN实际上的通信速率，可以用以下方式估算：
$$
\mathrm{BaudRate} = \frac{f_{\mathrm{FDCAN}}/\mathrm{Prescaler}}{1+\mathrm{TimeSeg1}+\mathrm{TimeSeg2}}
$$
#### 纠错
- **了解CRC校验的原理**

CAN定义的错误有：
- **位错误**：发送方在发出每一位的同时会读回总线。如果发的是显性（0）却读回隐性（1），说明被别的节点覆盖或线路异常，立即报错（仲裁段与 ACK 段除外）。
- **位填充错误**：CAN 规定每连续 5 个同电平必须插入 1 个反电平的填充位，保证信号总有跳变用于同步。如果检测掉6个相同电平，就知道帧出问题了。
- **格式错误**：帧的固定字段（CRC 界定符、ACK 界定符、EOF 等）出错，说明帧结构被破坏。
- **ACK 错误**：发送方发完数据后没有等到任何节点的显性确认。
- **CRC 错误**：CRC校验不通过，表明数据帧内容不正确。
##### 重传和离线机制
任何节点（不一定是发送方）一旦检测到上述错误，立即在总线上发出 6 个连续**显性**位的**错误标志**。这会在总线上构成一个总时间不小于6个显性位的脉冲。注意到这个操作会直接触发位填充错误，所有节点（包括发送方）都会注意到当前帧被破坏，将其丢弃，之后所有设备发8位隐性界定符。

当发送方发现帧被作废（或出现 ACK 错误）并发现总线重新变为隐性后，会**从头重新发送整个帧**，持续该机制直到这一帧被某个节点正确接收（收到 ACK）为止。

如果错误只是偶发干扰，无限重传没什么问题；但如果某个节点持续出错（断线、晶振漂移、波特率不匹配），它每发一帧就作废一帧，会把整条总线拖垮。为此 CAN 给每个节点准备了两个计数器：**TEC**（发送错误计数）与 **REC**（接收错误计数）：
- 计数器过高时节点先降级为**被动错误**（Error Passive）：仍然通信，但错误帧变成发6个连续**隐性位**，不再强占总线；
- **TEC > 255 时节点进入 Bus off**：收发器与总线脱开，只监听不上线，不拖累整条总线。进入busoff后，至少需要128个11位连续隐性位才可恢复，这在工作的总线中几乎是不可能的。（当然这是协议规定，实际上你可以在busoff以后自己想办法重开）

> [!Tip]  STM32的实际busoff行为
> 虽然标准没有规定busoff的时候节点能不能接收信息，但是STM32的策略是Busoff中既不能发送，也不能接收，设备**自动置位 CCCR.INIT** 停止总线活动，等待129个11位电平后恢复。比128多了一个，这是因为是清除 INIT 后，位流处理器要先等待一个 11 位空闲序列把自己同步到总线上，然后才开始计数恢复序列。

>[!Note] 【扩展】REC和TEC的计数策略
>
>TEC（发送错误计数）：
>- +8：发送失败（位错误、ACK错误、发送错误标志后读到显性）
>- -1：发送成功（让计数器可以在正确发送的时候计数器水位可以下降）
>阈值：≥128 进 Passive，>255 进 Bus Off
>
>REC（接收错误计数）：
>- +1：发现错误但未发错误标志（CRC错、填充错、格式错，不发标志可能是自己已经busoff或者passive了）
>- +8：**发现错误并发了错误标志**（因为发标志实际上也破坏了总线，所以也有一定惩罚防止某个接收坏了无限打断）
>- -1：接收成功
>阈值：≥128 进 Passive，**REC本身不会导致Bus Off**
#### 负载
在CAN总线上，同一时刻只能有一个报文被传输，计算CAN总线的负载，本质上是计算**单位时间内总线被各种报文占据的时间比例**。如果这个比例太高（比如80%），可能会出现设备无响应或响应不及时（CAN总线是纯优先级仲裁模式，这时候可能会饿死低优先级消息），同时，过多的接入设备可能导致总线的电气环境恶化，增加传输失败的可能性，造成重传风暴和Bus off。

在实际使用的时候，可以使用[CAN 总线负载计算器](https://lc6464.github.io/CANbus-Load-Calculator/)这样的计算器计算CAN总线上的负载。
### FDCAN
FDCAN的区别主要是**帧更长**（数据段8B→64B）、**更快**（BRS 位让一帧内的数据段切换到更高的数据位速率，仲裁段维持较慢速率，仲裁裕度和位同步机制不变，只在长数据段提速）、**CRC 更强**（15→17/21 bit）。

仲裁、纠错、重传等总线机制不变，因此同一总线可以同时收发经典帧和 FD 帧，但前提是**所有节点都支持 FD**。经典节点会把FD帧的FDF隐性位误判为格式错误，进而广播错误帧干扰总线。

> [!Note] 【扩展】总线长度和残桩（stub）
>
> 电信号在导线中的传播速度是有限的。CAN 使用的 120Ω 双绞线上大约为 5 ns/m（约为光速的 2/3）。而 CAN 的仲裁机制要求**所有节点在同一时刻看到同一位**：发送方发出的信号要传到最远的节点，对方的应答（比如仲裁中被压制、或 ACK 的显性确认）还要传回来，这一切都必须在一个位时间内完成。这正是上文小节中 Prop_Seg 存在的意义。，但位时间总量是固定的（由波特率决定），于是**波特率与总线长度相互制约：波特率越高，总线能拉得越短**。
>
> 电机等终端设备，往往是通过一小段支线接入总线节点，这一小段支线被被称为残桩（stub）。这段支线的末端是开路的，信号传到端点会像水波打到岸边一样**反射回来**，反射波与主干信号叠加，扭曲电平波形，可能导致节点采样出错。支线越长，反射越明显。总线两端的 120Ω **终端电阻**（与电缆差分阻抗匹配）正是负责吸收信号能量、防止反射，同时把总线空闲时的差分电压拉回隐性电平。部分设备内置了终端电阻，接入前要确认，避免接入过量的终端电阻导致总电阻被并联拉低、破坏阻抗匹配。
>
> 由此得出布线的规则：
> - 支线尽量短，一般建议 < 0.3 m，速率较低时可适当放宽
> - 拓扑尽量做成"手拉手"的直线（菊花链），避免星型连接把每根线都变成暗桩
> - 终端电阻只在总线**两端**各一个（共 2 个），中间节点不再添加
> - 各支线长度参差不齐会让反射波到达时间错开，情况更糟
>
> 在RC的实际使用中，板间距离通常很短、速率也不算极限，布线随意一些一般也能正常通信；但当出现通信不稳定、误码率偏高时，除了检查波特率和干扰，也应当检查物理拓扑。实际上 CAN 在物理层还是有很多讲究的，如果对这部分有兴趣可以阅读：[TI-Controller Area Network Physical Layer Requirements](https://www.ti.com/lit/an/slla270/slla270.pdf)

### STM32的CAN 外设

> [!Info] 
> 因为我们基本上只使用H723进行CAN控制，而H7系列和F1系列的CAN硬件实现有较大差别，**因此接下来我们短暂切换到H723ZGT6的MCU架构。**

出于电平标准、驱动能力等原因，STM32没有差分CAN口，而是以TTL电平的TX、RX作为CAN输出。所以，在总线和MCU之间需要专门的CAN收发芯片进行转接。收发芯片负责将MCU TX接口的TTL电平转化为差分电平信号CAN H/L，同时用RX接口同步回读总线状态，使得主控可以知道自己是否成功抢占了总线，是否有错误，或者ACK应答的情况。虽然CAN TX/RX有两条独立的收发线，但是考虑CAN总线结构可以知道，这是一种半双工通信。

H723ZGT6上提供 **FDCAN1/2/3** 三个外设，三者共享同一块 2560B的Message RAM，既支持经典 CAN 2.0，也支持 CAN FD。HAL 为每个 FDCAN 外设生成 `hfdcan1` 这样的句柄。

和串口的直接与寄存器交互不同，CPU将CAN配置需要的过滤器、配置信息和数据帧全部放在RAM中，然后由CAN控制器自动读写RAM，和DAM比较类似。这就意味着发送时 CPU 只做一件事：把帧头 + 数据一次性写进 Message RAM 的 Tx Buffer，而接收时 CPU 只在中断里把帧从 Rx FIFO 读出来。中间的串行化、位时序、仲裁、错误检测乃至自动重传全部由 FDCAN 硬件自行完成。

>[!Note] 【扩展】回读机制和TDC
>
> MCU 从FDCAN_TX发出每一位的同时，需要通过收发器从总线把实际电平读回来发送到FDCAN_RX引脚，与刚才发的值对比。这个环路大概是：FDCAN_TX → 收发器 → 总线 → 收发器 → FDCAN_RX，仲裁让位、位错误检测、ACK 监听全依赖它。但是，这个环路存在固有延迟，约百 ns 量级。
>
> **TDC（Transmitter Delay Compensation，发送延迟补偿）**：
> 经典 CAN 位时间长，回读延迟不明显，一般没有问题。但 CAN FD 数据段跑高速率时位时间被压缩（如 5 Mbps = 200 ns），若回读延迟大于 TSEG1，比对时读回来的已经是下一个位的内容，会**误判为位错误**。
>
> 对此，FDCAN 的对策是TDC：发出位之后，经过一段与回读延迟相当的可配置延迟（FDCAN_TDCR.TDCO）再采样比对。
>
> **前人经验指出**，对于我们常用的TJA1051收发器，回环延迟在40-250左右。CAN速率高于4Mbps时，若不配置TDC，比较容易出现错误帧，这和计算结构是比较符合的（4Mbps时位周时间为250ns）。目前实验室使用的CAN速率暂时没有高于4Mbps的。
>

RAM 被预先划成几类分区：

| 分区 | 深度（默认） | 元素大小 | 作用 |
| --- | --- | --- | --- |
| 标准 ID 过滤器列表 | 28 条 | 1 word | 11 位 ID 的过滤规则 |

##### 过滤器
过滤器是Message RAM开头预留的两张列表，`SIDFC` 和 `XIDFC` 两个寄存器分别给出它们的起始地址：
- **SIDFC** 管标准 ID 过滤器列表：一条规则只占 **1 word**，11 位 ID 的匹配方式、动作加上两个 ID 值（范围/掩码模式的上下限），正好塞进 32 bit；
- **XIDFC** 管扩展 ID 过滤器列表：一条规则要占 **2 word**，29 位 ID 加配置位塞不进一个 word。

所有过滤匹配都由硬件并行完成：一帧到达时，其 ID 同时与列表里每条规则比对，命中规则的动作者（送 FIFO 0 / 送 FIFO 1 / 送 Rx Buffer）即刻生效，全程不占用 CPU。
##### FIFO 和 Buffer
Rx FIFO 和 Rx Buffer 的元素格式、访问入口完全一样，区别在于**写入与读取的语义**：
- **Rx FIFO**：我们已经了解过FIFO，硬件按到达顺序写入，写指针自动前进。CPU 调 `HAL_FDCAN_GetRxMessage()` 只能按硬件读指针取出最先进入的一帧，取走即释放。FIFO的深度为3帧，取不过来时新帧会直接丢弃并通知 `MESSAGE_LOST`。它的语义是**缓冲并处理每一帧**
- **Rx Buffer**：两个固定缓存，通过过滤器规则里的 `FilterConfig`（`FDCAN_FILTER_TO_RXBUFFER0/1`）把某条规则直接指向某个格子。匹配帧到达时硬件**覆盖写入**对应格子，CPU 随时可以读，读取不主动释放数据，新帧直接覆盖旧帧。它的语义是**只关心某类消息的最新值**

 在多数情况下，使用FIFO的情况较多，Buffer只在某些特殊或紧急事件中才会用到。
##### 地址偏移
H723有3个CAN通道，而他们共用同一块RAM，这就需要我们给三个通道划分区域。
划分的方式就是偏移量：每个通道的分区配置寄存器（如`SIDFC`）里填的起始地址，都是相对 Message RAM 基址的**字偏移**，单位是 32-bit word（4B）。各分区首尾相接、互不重叠。FDCAN1 从偏移 0 开始，FDCAN2、FDCAN3 的整套分区紧随其后，每个通道区域里面可以自由分配不同元素占据的空间。

> [!Note] 【扩展】CAN的状态寄存器
> 我们提到过CAN协议定义了一些错误类型，这些错误在STM32中由CAN控制器自动处理，发错误帧、作废重传、维护计数都是内核自己完成的，内核只检测一些状态。主要是三个寄存器：
> - **PSR（Protocol Status Register，0x44）**
> 	- `LEC[2:0]`（Last Error Code）：**最近一次**协议错误的编码：`0` 无错误（自上次成功收发后）；`1` Stuff；`2` Form；`3` ACK；`4` Bit1（想发隐性却读到显性）；`5` Bit0（想发显性却读到隐性）；`6` CRC；`7` 无变化
> 	- `DLEC[2:0]`：同编码，记录 FD 格式帧数据段的错误（经典 CAN 用不到）
> 	- 状态位：`BO`（Bus off）、`EW`（警告，TEC/REC ≥ 96）、`EP`（被动错误）、`ACT[1:0]`（当前角色：同步中/空闲/接收/发送）
> 	- 更新规则：每发生一次协议错误 LEC 即被覆盖；一帧成功收发后清为 `0`；每次读 PSR 又复位为 `7`，不保留历史记录
> - **ECR（Error Counter Register，0x40）**
> 	- `TEC[7:0]` / `REC[6:0]`：上文纠错小节两个错误计数器的实时值（REC 达到 128 时由 `RP` 位指示被动错误）
> 	- `CEL[7:0]`（CAN Error Logging）：协议错误总次数，每发生一次让 TEC 或 REC 增长的错误就加一，读完清零，记满 255 次后溢出并置 IR 的 `ELO` 标志
> - **IR（Interrupt Register，0x50）**：全部事件标志的集合，写 1 清除。错误相关的有 `PEA`/`PED`（仲裁段/数据段出现协议错误）、`EW`/`EP`/`BO`（状态位跃迁）、`ELO`（CEL 溢出）、`MRAF`（Message RAM 访问失败，内核没来得及读写上文划定的分区）
>
> 各标志经 IE（逐个使能）、ILS（分配到 INT0/INT1 哪条线）、ILE（线总开关）流转为中断，HAL 层对应两个回调：协议错误进 `HAL_FDCAN_ErrorCallback()`（用 `HAL_FDCAN_GetProtocolStatus()` / `HAL_FDCAN_GetErrorCounters()` 读 PSR/ECR），状态跃迁进 `HAL_FDCAN_ErrorStatusCallback()`。
> 
> 更多参考：Reference Manual，P2574

> [!Note] 【扩展】F103的CAN实现
>在F103等STM32 的经典 CAN 外设叫 **bxCAN**（Basic Extended CAN），支持 CAN 2.0A/2.0B，最高 1Mbps。它的资源是：
> - **3 个发送邮箱**：最多同时缓存 3 个待发报文。多个报文排队时，可以按 ID 优先级发，也可以按进入邮箱的顺序发（由 `TXFP` 决定）。
> - **2 个接收 FIFO，每个 3 级深**：最多缓存 6 个收到的报文。溢出时是丢弃新报文还是覆盖旧报文，由 `RFLM` 决定。

#### 函数原型和基本实现

```c
/* 过滤器（启动前配置一次） */
HAL_FDCAN_ConfigFilter(&hfdcan1, &filter);          // 配置一条 ID 过滤器
HAL_FDCAN_ConfigGlobalFilter(&hfdcan1, FDCAN_REJECT, FDCAN_REJECT,
                             FDCAN_FILTER_REMOTE, FDCAN_FILTER_REMOTE);
                                                    // 未匹配帧的处置：拒绝 / 放行

/* 启动 */
HAL_FDCAN_Start(&hfdcan1);                          // 外设上线，参与总线
HAL_FDCAN_ActivateNotification(&hfdcan1, FDCAN_IT_RX_FIFO0_NEW_MESSAGE, 0);

/* 发送 */
HAL_FDCAN_AddMessageToTxFifoQ(&hfdcan1, &tx_header, tx_data);

/* 接收（中断回调里调用，轮询时也可直接调用） */
HAL_FDCAN_GetRxMessage(&hfdcan1, FDCAN_RX_FIFO0, &rx_header, rx_data);
HAL_FDCAN_GetRxFifoFillLevel(&hfdcan1, FDCAN_RX_FIFO0);   // 查询 FIFO 里积压了几帧
```

在 CAN 里，一帧 = **帧头（header）+ 数据**两部分，函数原型也围绕这个结构展开：

- `hfdcan`：外设句柄，CubeMX 生成的 `hfdcan1` 等，用法和串口的 `huart1` 完全一致。
- `tx_header` / `rx_header`：`FDCAN_TxHeaderTypeDef` / `FDCAN_RxHeaderTypeDef`。发送时 CPU 填好帧头交给 HAL 写进 Tx Buffer；接收时 HAL 把收到的帧头填进来，ID 在 `rx_header.Identifier` 里。
- 数据数组：经典 CAN 帧固定 8 字节（FD 帧最多 64 字节），帧长由帧头的 `DataLength` 字段声明（用 `FDCAN_DLC_BYTES_8` 这类宏）。

与串口"一次启动收 Size 个字节"不同：CAN 每次 `AddMessageToTxFifoQ` 发**一帧**，每次 `GetRxMessage` 取**一帧**。发送函数返回只代表"帧已放进 RAM"，真正上线、仲裁、重传都由硬件自治——这也是上文结构框图中 Tx/Rx Handler 存在的意义。发送回执可以通过帧头的 `TxEventFifoControl` 选择记进 Tx 事件 FIFO（呼应上文内存模型小节）。

发送示例（经典 CAN 8 字节帧，RoboMaster 电调的标准格式）：

```c
FDCAN_TxHeaderTypeDef tx_header;
uint8_t tx_data[8] = {0};

tx_header.Identifier = 0x201;                 // 标准帧 ID
tx_header.IdType = FDCAN_STANDARD_ID;
tx_header.TxFrameType = FDCAN_DATA_FRAME;
tx_header.DataLength = FDCAN_DLC_BYTES_8;
tx_header.ErrorStateIndicator = FDCAN_ESI_ACTIVE;
tx_header.BitRateSwitch = FDCAN_BRS_OFF;      // 不使用 FD 数据段加速
tx_header.FDFormat = FDCAN_CLASSIC_CAN;       // 经典 CAN 帧
tx_header.TxEventFifoControl = FDCAN_NO_TX_EVENTS;
tx_header.MessageMarker = 0;

HAL_FDCAN_AddMessageToTxFifoQ(&hfdcan1, &tx_header, tx_data);
```

接收前必须先配置过滤器——呼应上文 [ID](#id) 小节的结论：CAN 的 ID 是消息的分类标签而非设备地址，过滤器决定"这条消息我要不要"。HAL 把过滤器写成 `FDCAN_FilterTypeDef`，本质上就是在 Message RAM 的过滤器列表里登记一条规则：

```c
FDCAN_FilterTypeDef filter;
filter.IdType = FDCAN_STANDARD_ID;
filter.FilterIndex = 0;                       // 标准过滤器列表的第 0 条
filter.FilterType = FDCAN_FILTER_RANGE;       // 范围模式：ID1~ID2 之间都放行
                                              // 另有 DUAL（两个独立 ID）、MASK（掩码模式）
filter.FilterConfig = FDCAN_FILTER_TO_RXFIFO0;// 匹配的帧送进 Rx FIFO 0
filter.FilterID1 = 0x000;
filter.FilterID2 = 0x7FF;

HAL_FDCAN_ConfigFilter(&hfdcan1, &filter);
HAL_FDCAN_ConfigGlobalFilter(&hfdcan1, FDCAN_REJECT, FDCAN_REJECT,
                             FDCAN_FILTER_REMOTE, FDCAN_FILTER_REMOTE);
                                              // 未匹配的帧直接拒绝，远程帧按过滤器规则处理
```

这套过滤器和 bxCAN 的筛选器语义一致（见上文 F103 的 Note），只是实现载体从"28 组专用筛选器"变成了 Message RAM 里的过滤器列表。

> [!Tip] 全收还是全拒
> 图省事的话，可以让所有帧都进中断：把 `ConfigGlobalFilter` 配成 `FDCAN_ACCEPT_IN_RX_FIFO0`，过滤器只留一条放行所有 ID 的范围规则。但工程上更推荐默认拒绝 + 白名单。

接收回调——注意与串口最大的心智差异：**回调里不需要重启接收**。Rx FIFO 常驻 Message RAM，硬件自动写入，我们只管取：

```c
/* USER CODE BEGIN 4 */
void HAL_FDCAN_RxFifo0Callback(FDCAN_HandleTypeDef *hfdcan, uint32_t RxFifo0ITs)
{
    FDCAN_RxHeaderTypeDef rx_header;
    uint8_t rx_data[8];

    if ((RxFifo0ITs & FDCAN_IT_RX_FIFO0_NEW_MESSAGE) != 0) {
        /* 一次中断只代表"至少来了一帧"，FIFO 里可能已积压多帧，循环取干净 */
        while (HAL_FDCAN_GetRxFifoFillLevel(hfdcan, FDCAN_RX_FIFO0) > 0) {
            HAL_FDCAN_GetRxMessage(hfdcan, FDCAN_RX_FIFO0, &rx_header, rx_data);
            // 按 rx_header.Identifier 分发处理 rx_data
        }
    }
    if ((RxFifo0ITs & FDCAN_IT_RX_FIFO0_MESSAGE_LOST) != 0) {
        // FIFO 满了还来新帧，硬件丢帧了——处理速度跟不上，检查回调耗时或总线负载
    }
}
/* USER CODE END 4 */
```

只取一帧也能跑，但高频总线下会越积越多，最终触发 `MESSAGE_LOST`（该事件需要单独 ActivateNotification 才能收到）。

> [!Tip] 为Bus off兜底
> 上文纠错小节说过，TEC > 255 时节点进入 Bus off——硬件脱线，帧发不出去也收不进来，程序"没死但失联"。建议在初始化时用 `HAL_FDCAN_ActivateNotification()` 一并使能 `FDCAN_IT_BUS_OFF`，事件会进入 `HAL_FDCAN_ErrorStatusCallback()`，检测到该标志后调用 `HAL_FDCAN_Stop()` + `HAL_FDCAN_Start()` 重新上线。不过 Bus off 通常意味着总线存在真实问题（波特率不匹配、断线、终端电阻缺失），重启只是让程序活下来，根因还得回到物理层和纠错层面去查。

## SPI
### 四线与时序
- **SPI 的四根线分别干什么？为什么它能全双工？**
- **片选为什么要用"低有效"？多个从机怎么接？**
- **SPI 为什么没有应答机制？**

SPI 是**同步**通信，有一根独立的时钟线，所以不需要像 UART 那样靠波特率对齐：

- `SCK`：时钟，由主机产生。
- `MOSI`：Master Out Slave In，主机发、从机收。
- `MISO`：Master In Slave Out，从机发、主机收。
- `CS`（或 `SS`）：片选，低电平有效，主机用它指定"现在跟谁说话"。

因为有独立的收发线，SPI 可以**全双工**：主机在 MOSI 上发的同时，从机在 MISO 上回。很多 SPI 器件的读写是同一个操作，发一个命令字过去，同一个时钟周期里它就回一个字节。

SPI 没有应答、没有校验、没有重传，所以 SPI 一般只用在板内或极短的走线，距离几厘米到十几厘米左右。

### SPI的模式
- **CPOL 和 CPHA 分别控制什么？**

时钟极性和时钟相位这两个参数，决定了"数据在哪个边沿被采样"：
- **CPOL（Clock Polarity）**：空闲时时钟是高还是低。0 = 空闲低，1 = 空闲高。
- **CPHA（Clock Phase）**：在第一个边沿采样还是第二个边沿采样。0 = 第一个边沿，1 = 第二个边沿。

两者组合就是 Mode 0 ~ Mode 3。大多数器件用 Mode 0（空闲低、上升沿采样）或 Mode 3（空闲高、下降沿采样），这两个模式实际上都是"在时钟的有效沿采样、在另一个沿改变数据"，所以兼容性最好。

>[!Tip] 通信协议的层次
>从使用什么线缆和电平标准，到数据帧格式和其承载的数据收发、应答、仲裁机制，你可能会感觉到，我们所说的“通讯协议”实际上是一个复杂的分层系统，而很多时候不同协议名词下面所包含的层次实际上也有差别。如果你想对这个分层概念有更深入的认识，最好的办法其实是参考计算机网络的七层或者四层模型，相信你会有更多的收获。

> [!Tip] 标准为什么重要
> 这一章我们介绍了许多协议，也带领大家学习了许多不同的通信协议和其具体的实现标准。你会发现CAN和许多私有协议虽然出身于企业，但他们最终都在走向流行的过程中成为了国际标准的一部分。标准为什么重要？因为标准严谨，有刚性，这就意味着无论是什么国家什么厂商什么时候制造出来的设备，只要满足同一个标准，就一定可以正确地配合在一起工作，而无需纠结其中具体的技术指标。这节省了大量设计、沟通、制造的成本。因此，标准化几乎是任何一个**成熟开放**的**工程领域**发展的必经之路，从通讯协议、机械零件到土木工程，莫不如是。
