### 匿名命名空间
`static` 在 C++ 中承担了太多互不相关的含义。从字面意思来看，`static` 意思是是“静态的”。可到底什么是静态的？在类内，它表示**属于类而非实例**；在函数内，它表示**生命周期贯穿程序运行**；在命名空间作用域，它才表示**内部链接**。这种一词多义非常不自然（你们难道缺单词用吗），并且容易产生混淆和指代不明。同时 `static` 只能修饰函数和变量，无法给 `struct`、`class`、`typedef` 或 `using` 别名赋予内部链接。所以，既然C++引入了命名空间，就可以顺便把这些问题也用命名空间解决了。

实际上，命名空间就是C++给 `static` 钦定的接班人，在C++98/03时期，曾将命名空间作用域的 `static` 标记为弃用，理由就是匿名命名空间是“更好的替代”。但C++11又撤销了这一弃用，主要是为了保持与C语言的兼容性。因此，在C++11以后两者在标准层面都是完全合法的，并且**完全等价**。

现代 C++ 推荐用**匿名命名空间**替代全局 `static`，因为匿名命名空间能给任何实体（包括类、枚举）制造内部链接，而 `static` 只能用于函数和变量。

我们已经介绍过普通的具名命名空间，而匿名空间就意味着他是不可选中的，也就永远对于其它编译空间隐藏，无法被引用。使用方法如下：
```C++
namespace {
    int foo();
}

foo(); 	// 这里其实也可以调用foo()
```

注意到，大括号以外的同文件部分仍然和 `foo()` 位于同一编译单元内，所以同文件内仍然可以访问，而离开该文件则不行。大括号只是定义了一个没有名字的命名空间，并不构成访问边界。

当然，匿名命名空间也不是十全十美。比如，在一个复杂冗长的源文件中，你可能很容易注意到单一函数的 `static`（尽管你需要打很多次），但却可能注意不到 `namespace` 的作用范围。

> [!Tip] 【扩展】依赖名查找与链接属性的历史纠葛
> 在[一些讨论中](https://stackoverflow.com/questions/154469/why-should-you-prefer-unnamed-namespaces-over-static-functions/155734#155734#1)，认为在C++03版本中匿名命名空间实际上具有外部连接，尽管名字被唯一化，它们可能还是可能意外被ADL（也叫[Koenig lookup](https://learn.microsoft.com/zh-cn/cpp/cpp/argument-dependent-name-koenig-lookup-on-functions?view=msvc-170)）捕获。但是，在C++11以后匿名命名空间成员被明确规定为内部链接，所以可以认为完全等效

## 【扩展】原子操作
[Cortex-M 系列处理器在嵌入式 C 语言中的原子操作](https://www.embeddedsoft.net/atomic-operations-in-embedded-c-for-cortex-m/#c11-atomics-in-embedded-c)
遇事不决关中断不是最好的解决方案，因为这会恶化实时性表现，并且很可能对很多DMA操作没用。

在 C11 之前，如果想要强制C代码实现原子操作，基本只能依赖编译器特定的内建函数（Intrinsics）或者内嵌汇编指令（比如ARM 的 `LDREX/STREX`），但这显然没什么跨平台兼容性，而且语法复杂；又或者在RTOS等系统中直接使用开销更大的线程锁（而实际上，你可能只是想做一次load+store）。C11 标准通过引入 `_Atomic` 关键字和 `<stdatomic.h>` 头文件，才第一次在语言层面提供了原子操作支持。

是的，C语言在C11以后也有了语言层面的原子操作支持，而C++ 提供了一层更符合语言习惯、更灵活的抽象，使其用起来更自然、安全。现在这些特征已经在高版本的GCC arm和armclang中被支持。

### 链接器与inline

#### 内部链接和外部链接


现代编译器中，`inline`早就不能支配编译器是否内联某些代码，`inline`在现代C++的核心作用其实是ODR豁免。

> [!Tip] TU和ODR规则

#### inline变量
在C++17以后引入的inline变量使得在头文件定义的inline变量会使**每个翻译单元（.cpp文件）各自拥有一个该变量的独立实体，但链接器最终会强制将它们合并成一个唯一的全局实体**。因此在实际运行时，inline变量就是一个单一地址的全局变量，与定义-extern模式完全相同，并且拥有更加优雅的编程体验。最妙的是，它可以让我们直接在头文件中定义变量而不受multiple define的束缚，并设计header only的代码库。
#### inline constexpr
inline constexpr给需要在头文件中定义的常量提供了新的方法，可以用于取代宏参数。它既有inline的ODR豁免，又有constexpr的编译器推断来保证它在不同TU的一致性，高效而安全。

>[!Note] inline constexpr与const变量的区别
>在头文件中定义`const double kGravity = 9.81`不会报 "multiple definition"。这是因为在命名空间作用域（包括全局作用域）中，默认情况下（没有 extern）的 const 变量具有内部链接。这意味着每个包含该头文件的 .cpp 文件都会得到自己的一份独立拷贝，而不是共享同一个全局变量。这意味着&kGravity 在不同 TU 中不同，内存被浪费（虽然通常很小），且如果你依赖地址唯一性会出 bug。
>
>推荐的做法是在C++17及以后用 `inline constexpr double kGravity = 9.81l`，他不是内部连接的，所有 TU 共享同一个实例，&kGravity 在所有 TU 中相同。
