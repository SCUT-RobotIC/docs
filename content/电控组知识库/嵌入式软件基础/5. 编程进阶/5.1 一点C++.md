### 链接器与inline
#### 内部链接和外部链接
要理解`inline`在C++里的真实身份，要先回到链接层面。链接器组装各个`.o`文件时，最关心的就是符号的名字和归属，由此分出两种链接属性：
- **外部链接**：符号对整个工程可见。`a.cpp`里定义的普通函数和全局变量，`b.cpp`里声明一下`extern`就能用；
- **内部链接**：符号只在当前翻译单元内可见。C语言里用`static`修饰的函数/全局变量、匿名命名空间里的成员，作用域停留在`.cpp`文件。

这个模型带来一条铁律：**ODR（One Definition Rule，单一定义规则）**：一个有外部链接的函数或变量，在整个工程里只能定义一次，定义两次链接器直接报`multiple definition`。

这条铁律和头文件天生冲突：头文件会被`#include`进很多个`.cpp`，在里面写函数定义（非模板、非inline），每个包含它的翻译单元都生成一份定义，链接时当场爆炸。传统C语言的解法是"头文件只放声明，`.cpp`里放定义"这套分工；而C++要处理模板、类内定义的成员函数这些**必须写在头文件里**的东西，唯一的豁免就是使用inline。

> [!Tip] TU和ODR规则
> **翻译单元（TU, Translation Unit）**：一个`.cpp`文件经过预处理（把`#include`的头文件内容原样展开、宏替换完毕）后得到的完整源码，编译器实际编译的就是它。所以"一个.cpp"在链接器眼里其实是"一份cpp加上一串头文件的展开"。
>
> **ODR规则**分两层：每个TU内部，任何一个实体只能定义一次（这个好理解）；跨TU，有外部链接的实体在整个工程中也只能定义一次——**但`inline`函数/变量例外**：它允许在多个TU中各有一份定义，条件是所有定义必须逐字节相同（通常都来自同一个头文件，天然满足），链接器最后只保留一份、所有TU共享。
>
> 所以现代C++里`inline`的准确读法不是"请把它内联展开"，而是"**此定义允许多份，合并后共享**"——它改变的是链接行为，不是代码生成方式。
#### inline变量
在C++17以后引入的inline变量使得在头文件定义的inline变量会使**每个翻译单元（.cpp文件）各自拥有一个该变量的独立实体，但链接器最终会强制将它们合并成一个唯一的全局实体**。因此在实际运行时，inline变量就是一个单一地址的全局变量，与定义-extern模式完全相同，并且拥有更加优雅的编程体验。最妙的是，它可以让我们直接在头文件中定义变量而不受multiple define的束缚，并设计header only的代码库。
#### inline constexpr
inline constexpr给需要在头文件中定义的常量提供了新的方法，可以用于取代宏参数。它既有inline的ODR豁免，又有constexpr的编译器推断来保证它在不同TU的一致性，高效而安全。

>[!Note] inline constexpr与const变量的区别
>在头文件中定义`const double kGravity = 9.81`不会报 "multiple definition"。这是因为在命名空间作用域（包括全局作用域）中，默认情况下（没有 extern）的 const 变量具有内部链接。这意味着每个包含该头文件的 .cpp 文件都会得到自己的一份独立拷贝，而不是共享同一个全局变量。这意味着&kGravity 在不同 TU 中不同，内存被浪费（虽然通常很小），且如果你依赖地址唯一性会出 bug。
>
>推荐的做法是在C++17及以后用 `inline constexpr double kGravity = 9.81l`，他不是内部连接的，所有 TU 共享同一个实例，&kGravity 在所有 TU 中相同。


> [!Question] 在头文件中定义constexpr的结果是什么？
> 分版本讨论。C++17之前：`constexpr`隐含`const`，命名空间作用域的`const`默认内部链接——于是每个包含该头文件的TU各得一份独立拷贝，编译链接都不报错，但`&kConst`在不同`.cpp`里地址不同，就是上面Note里描述的状态。C++17起：配合`inline`（或直接用`inline constexpr`）得到全工程唯一的实体；如果不加`inline`，行为仍和C++17之前相同。**"在头文件定义常量不报错"和"全工程只有一份"是两件事**，前者靠内部链接，后者靠`inline`。

inline在新标准和旧标准下发生了明显的**语义迁移**，这是一个非常值得注意的例子。

### 匿名命名空间
`static` 在 C++ 中承担了太多互不相关的含义。从字面意思来看，`static` 意思是是“静态的”。可到底什么是静态的？在类内，它表示**属于类而非实例**；在函数内，它表示**生命周期贯穿程序运行**；在命名空间作用域，它才表示**内部链接**。这种一词多义非常不自然（你们难道缺单词用吗），并且容易产生混淆和指代不明。同时 `static` 只能修饰函数和变量，无法给 `struct`、`class`、`typedef` 或 `using` 别名赋予内部链接。所以，既然C++引入了命名空间，就可以顺便把这些问题也用命名空间解决了。

实际上，命名空间就是C++给 `static` 钦定的接班人，在C++98/03时期，曾将命名空间作用域的 `static` 标记为弃用，理由就是匿名命名空间是“更好的替代”。但C++11又撤销了这一弃用，主要是为了保持与C语言的兼容性。因此，在C++11以后两者在标准层面都是完全合法的，并且**完全等价**。

现代 C++ 推荐用**匿名命名空间**替代全局 `static`，因为匿名命名空间能给任何实体（包括类、枚举）制造内部链接，而 `static` 只能用于函数和变量。

我们已经介绍过普通的具名命名空间，而匿名空间就意味着他是不可选中的，也就永远对于其它编译空间隐藏，无法被引用。使用方法如下：
```C++
namespace {
    int foo();
}

foo(); 	// 这里其实也可以调用foo()
```

注意到，大括号以外的同文件部分仍然和 `foo()` 位于同一编译单元内，所以同文件内仍然可以访问，而离开该文件则不行。大括号只是定义了一个没有名字的命名空间，并不构成访问边界。

当然，匿名命名空间也不是十全十美。比如，在一个复杂冗长的源文件中，你可能很容易注意到单一函数的 `static`（尽管你需要打很多次），但却可能注意不到 `namespace` 的作用范围。

> [!Tip] 【扩展】依赖名查找与链接属性的历史纠葛
> 在[一些讨论中](https://stackoverflow.com/questions/154469/why-should-you-prefer-unnamed-namespaces-over-static-functions/155734#155734#1)，认为在C++03版本中匿名命名空间实际上具有外部连接，尽管名字被唯一化，它们可能还是可能意外被ADL（也叫[Koenig lookup](https://learn.microsoft.com/zh-cn/cpp/cpp/argument-dependent-name-koenig-lookup-on-functions?view=msvc-170)）捕获。但是，在C++11以后匿名命名空间成员被明确规定为内部链接，所以可以认为完全等效

## 类型的转换与推导
C语言里所有转换都写成`(目标类型)表达式`这一个样子。它的问题在于太万能了，去掉`const`、把指针指到完全无关的类型、改个数值精度四种性质完全不同的操作共用同一副面孔，读代码的人只能自己猜写的人到底想干什么，编译器也没法在你干蠢事时提醒你。
C++把转换拆成四个**具名**转换，让意图显式化：

| 写法 | 用途 | 危险程度 |
| --- | --- | --- |
| `static_cast` | 相关类型间的合理转换：数值类型之间、`enum`与整数、`void*`还原 | 低，编译期检查 |
| `const_cast` | 增删`const`/`volatile`属性 | 中，仅限"接口要求非const但我不改"的场景 |
| `reinterpret_cast` | 位模式重新解释：指针与整数、无关指针类型之间 | 高，纯粹告诉编译器闭嘴 |
| `dynamic_cast` | 沿继承层次向下转换，运行期检查 | 需要RTTI支持（见5.3，嵌入式通常禁用） |
最常见的两种：

```cpp
float duty = static_cast<float>(count) / period;   //数值运算前消除整数除法
uint32_t reg = *reinterpret_cast<volatile uint32_t*>(0x40020014U);  //按手册访问寄存器地址
```

>[!Tip] 拿不准就用`static_cast`，用它编译不过说明你在干危险的事
>`static_cast`覆盖了90%的合法转换需求；当它编译不过、你必须退而求其次用`reinterpret_cast`时，这个"别扭"本身就是编译器在提醒你：这里值得停下来检查，或者写一条注释说明为什么必须这么转。代码评审时，具名转换也让`reinterpret_cast`一眼可见——全局搜索这个词，就知道工程里有几处"信任我"式的裸地址操作。

和"手动指定类型"相对的另一件事是"让编译器推出类型"。模板函数的参数推导早在C++98就有了，C++11把这套机制开放给普通变量——`auto`。写`auto x = expr;`时，编译器按照模板推导的同一套规则，从初始化表达式推出`x`的类型。

`auto`最直接的受益者是迭代器这类"名字长得离谱"的类型：

```cpp
for (std::array<Chassis*, 4>::iterator it = robots.begin(); ...)  //C++98的写法
for (auto it = robots.begin(); ...)                               //auto接管
```

但`auto`真正重要的用途不是"省字"，而是**消除冗余和避免抄错**：`auto motor = DJIMotor(0x201);`里类型名只出现一次；更关键的是变量声明的类型永远和初始化表达式精确匹配——手动写类型时抄错、截断（比如把`uint32_t`写成`int`）这类隐患从根上消失。

两条使用纪律：

- **`auto`必须伴随初始化**，不能声明一个"待定"的变量，这反而堵死了C里"未初始化变量"的大坑；
- **类型是代码的一部分**。当类型本身承载信息（比如`float duty`告诉读者这是占空比），就明写；当类型只是实现细节（迭代器、lambda），才交给`auto`。通篇`auto`的代码和通篇`(类型)`强转的代码一样难读。

`decltype`是配套的另一面：`auto`"从值推类型"，`decltype`"从表达式取类型"，不实际求值。典型用法是声明一个"类型跟着别人走"的变量：

```cpp
decltype(x) y;      //y的类型与x完全相同，包括const和引用
```

`auto`和`decltype`的推导规则有几个反直觉的细节（比如`auto`默认丢弃引用和顶层`const`，`auto&&`配合引用折叠成为万能引用），这些属于模板元编程的范畴，遇到再查，不必背。

### CTAD
C++17把模板的推导能力从函数扩展到了**类模板**。此前构造一个模板类对象必须把类型参数写全：

```cpp
std::array<float, 4> joints{};        //必须手动写出<float, 4>
std::lock_guard<std::mutex> lk(mtx);  //必须写出<std::mutex>
```

C++17之后，编译器从构造函数的实参直接推导模板参数——这叫**类模板实参推导（CTAD）**：

```cpp
std::lock_guard lk(mtx);              //从mtx推出lock_guard<std::mutex>
std::pair p(1, 2.0);                  //推出pair<int, double>
```

推导不是猜，依据是**推导指引**：标准库为容器都写好了，自定义类模板也可以用`ClassName(...) -> ClassName<T>`的语法声明。日常使用只需要记住结论：**凡是初始化信息足够的场合，模板参数可以让编译器代劳**。CTAD需要C++17，用在工程里前先确认5.3里"只用C++11/14"的约束是否放宽。
## 原子操作
[Cortex-M 系列处理器在嵌入式 C 语言中的原子操作](https://www.embeddedsoft.net/atomic-operations-in-embedded-c-for-cortex-m/#c11-atomics-in-embedded-c)
遇事不决关中断不是最好的解决方案，因为这会恶化实时性表现，并且很可能对很多DMA操作没用。

在 C11 之前，如果想要强制C代码实现原子操作，基本只能依赖编译器特定的内建函数（Intrinsics）或者内嵌汇编指令（比如ARM 的 `LDREX/STREX`），但这显然没什么跨平台兼容性，而且语法复杂；又或者在RTOS等系统中直接使用开销更大的线程锁（而实际上，你可能只是想做一次load+store）。C11 标准通过引入 `_Atomic` 关键字和 `<stdatomic.h>` 头文件，才第一次在语言层面提供了原子操作支持。

是的，C语言在C11以后也有了语言层面的原子操作支持，而C++ 提供了一层更符合语言习惯、更灵活的抽象，使其用起来更自然、安全。现在这些特征已经在高版本的GCC arm和armclang中被支持。
## lambda表达式
lambda解决的是一个朴素的问题：**一段只打算用一次的逻辑，值不值得为它起个名字、挪到别处去？**C++11以前答案是"不得不值得"——标准库的排序、查找允许传入自定义比较逻辑，但你必须把这段逻辑写成独立的函数或仿函数类，定义和使用隔得很远：

```cpp
bool byLength(const MotorCmd& a, const MotorCmd& b) {
  return a.priority < b.priority;
}
std::sort(cmds.begin(), cmds.end(), byLength);   //逻辑在这里，定义在别处
```

lambda允许把逻辑**就地**写在使用点上：

```cpp
std::sort(cmds.begin(), cmds.end(),
          [](const MotorCmd& a, const MotorCmd& b) {
            return a.priority < b.priority;
          });
```

`[]`是捕获列表，是lambda区别于普通函数的核心：它声明"我要用外面的哪些变量、怎么用"。`[x]`按值拷贝x进lambda，`[&x]`按引用使用x，`[=]`/`[&]`全部按值/按引用——惰性写法，能不敲就不敲。于是**带状态的"函数"可以随手造出来**，这是普通函数做不到的：

```cpp
int base = 1500;
auto clamp = [base](int v) { return v < base ? base : v; };   //这个"函数"记住了base
```

捕获还有几个值得知道的细节：**按值捕获默认不可改**（要改得加`mutable`，改的也是副本，不会影响外面）；`[&]`捕获引用时，lambda的生命周期不能超过被引用变量的生命周期——把lambda存进回调队列、异步执行时，悬空引用和野指针是同一件事。成员函数里`[this]`捕获的是指针，对象先死了lambda还在排队的写法同理危险。

lambda的本质是"编译器帮你生成了一个匿名仿函数类"，所以`auto f = [](...){...};`这种写法零开销——它不是函数指针，没有间接调用。需要传给C风格回调接口时才退化成函数指针（无捕获的lambda可以），有捕获的传不了，这是嵌入式中用lambda绕不过的限制。

## 移动语义
函数返回一个大的`std::array`或者一个持有缓冲区的对象时，数据是怎么回到调用方的？

传统答案里有"拷贝构造"和"赋值"两个动作，它们共同的哲学是：**我要一份新的，你得把旧的完好保留**。源对象和目标对象各自持有一份完整数据，哪怕源对象马上就要销毁。当对象内部管理着一块堆内存或一片大数据时，这个哲学意味着无谓的深拷贝。

C++11注意到：很多时候**源对象是个临时的，它马上就要死**。函数返回值、`make_array(...)`的产物、`std::move(x)`标记过的对象——它们的数据即将随对象一起销毁，与其深拷贝一份再销毁原件，不如**把原件直接搬走**，源对象留个空壳。这个"搬"的动作就是**移动**，对应的构造/赋值函数叫**移动构造/移动赋值**。

```cpp
Buffer(Buffer&& other) noexcept    //&&表示绑定到"将要销毁"的对象（右值）
    : data_(other.data_), len_(other.len_) {  //接管指针
  other.data_ = nullptr;           //源对象置空，防止析构时double free
  other.len_ = 0;
}
```

`std::move(x)`本身不移动任何东西——它只是一个类型转换，把`x`标记成"可以搬"（右值引用），真正的搬发生在移动构造/赋值里。名字起得有误导性，读作"授权搬走"更准确。

移动语义改变了什么？

- **容器的大搬移变便宜了**：`vector`扩容、对象进出容器，从"逐元素深拷贝"变成"接管指针"，O(n)次深拷贝变成n次指针交接；
- **返回大对象不再疼**：返回值优化（RVO/NRVO）配合移动语义，"函数返回大结构"从性能禁区变成了正常写法；
- **资源管理类的正确姿势**：第0/3/5法则升级——自定义析构函数的类，通常也要自定义（或`default`）移动构造/赋值，否则默认行为会逐成员拷贝指针，产生双重释放。
