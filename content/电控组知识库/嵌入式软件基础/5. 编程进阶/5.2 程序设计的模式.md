## 依赖注入（DI）和控制反转（IoC）

用OOP的思路写一个底盘类，最顺手的写法是什么？大概是让底盘自己持有电机对象：

```cpp
class Chassis {
  DJIMotor lf, rf, lb, rb;   //底盘内部直接创建具体的电机
 public:
  void update() {
    lf.setSpeed(...);        //直接调用具体电机的接口
    ...
  }
};
```

问题在于，`Chassis`已经被固化为C620电机了。哪天换达妙电机，或者想在电脑上用一套虚拟电机先调试底盘算法就不好搞了，它的每一个细节都建立在电机是大疆的这个假设上。

怎么办？最好的办法是将电机抽象成接口，然后让具体对象和电机通过接口连接。**我们先把"能设转速的东西"抽象成一个接口：

```cpp
class IMotor {
 public:
  virtual void setSpeed(float rpm) = 0;
  virtual ~IMotor() = default;
};

class Chassis {
  IMotor& lf, & rf, & lb, & rb;    //只依赖抽象接口
 public:
  Chassis(IMotor& lf_, IMotor& rf_, IMotor& lb_, IMotor& rb_)
      : lf(lf_), rf(rf_), lb(lb_), rb(rb_) {}
};
```

`DJIMotor`直接继承IMotor的接口即可：

```cpp
class DJIMotor : public IMotor {   //继承接口，实现setSpeed
 public:
  void setSpeed(float rpm) override {
    //翻译成CAN报文发给C620电调
  }
};

DJIMotor lf(0x201), rf(0x202), lb(0x203), rb(0x204);
Chassis chassis(lf, rf, lb, rb);   //组装发生在使用方
```

这就是**依赖注入（Dependency Injection）**：一个对象需要的依赖，不由它自己创建，而是由外部构造好、通过构造函数（或参数）传给它。

现在，"用哪个电机"的决定权，原来写在`Chassis`内部，现在移到了外部的组装代码里。对象把自己依赖的创建权交了出去，程序流程的控制方向被"反转"了，这被称为**控制反转（Inversion of Control）**。 IoC是思想，DI是实现这个思想最常用的手法。

其实，这正是**依赖倒置原则**的落地，高层模块（底盘的业务逻辑）不再直接依赖低层模块（具体电机），两者都依赖抽象（`IMotor`接口）。
